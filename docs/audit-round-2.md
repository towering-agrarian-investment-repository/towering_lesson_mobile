## Current backend contract

- `GET /api/v1/member/homework/{homeworkId}` returns `data.submissions` with the complete history for that homework and authenticated member, ordered by `revisionNo` descending. `GET /api/v1/member/homework-submissions/homework/{homeworkId}` returns the same history. The detail response is authoritative for this screen.
- `GET /api/v1/member/lesson-logs/count` returns `ApiResponse<number>` with the total in `data`.
- `GET /api/v1/member/lesson-logs` returns cursor-paginated `data: { items, nextCursor, hasMore }`, ordered by `createdAt` descending then `id` descending.
- `GET /api/v1/member/{memberId}/tickets` returns the same cursor page shape and ordering. It accepts optional repeated `statuses`; omitted statuses mean `ACTIVE`, `IN_USE`, `EXPIRED`, and `TRANSFERRED`, excluding `CANCELLED`. The home and ticket-list screens explicitly request `ACTIVE` and `IN_USE` to preserve their previous filter.
- Both lists accept optional `limit` (default 20, range 1–100) and `cursor` (omitted on page one). No total count is returned with a page.

## Decisions and remaining backend question

- Retry a GET once after successful session verification and JWT refresh. Do not replay writes without backend idempotency guarantees.
- Run the startup version check asynchronously. Enforce a mandatory update once confirmed; the existing two-second check timeout still fails open on error.
- Use cursor pagination with 20 items per page for tickets and lesson logs.
- Backend follow-up: assess ticket lookup by ID or type filtering to avoid scanning pages in the rare booking-success fallback and filtered ticket tabs.
